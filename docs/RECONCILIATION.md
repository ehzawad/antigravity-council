# Reconciliation with Codex Council and Cursor Cult

Reviewed **October 22, 2026** against codex-council 1.3.3, cursor-cult 0.7.0, and Claude Code 2.1.307. The Antigravity side was rechecked for 1.0.0 on **November 20, 2026** against `agy` 1.5.12 and the official CLI docs. The three plugins share one idea: the host owns intent, creates roles dynamically from the live task, runs independent workers, and reconciles evidence rather than votes. They differ because the vendor CLIs execute work in very different ways.

## What is shared

| Principle | Codex Council | Cursor Cult | Antigravity Council |
|---|---|---|---|
| Host owns intent and reconciliation | yes | yes | yes |
| No persona catalog, no vote-based answer | yes | yes | yes |
| Dynamic roles from the live task | `roles.json` | `roles.json` | `roles.json` |
| Immutable intent across rounds | brief per run | Intent Capsule | Intent Capsule, hash-bound to a task key |
| Detached supervisor, follow/status/cancel | yes | yes | yes |
| Turn-scoped skill pre-approval of runner commands | yes | yes | yes (0.2.0) |
| Install from the GitHub marketplace | yes | yes | yes (0.2.0) |

## Where Antigravity differs, and why

**Execution model.** Codex Council runs each contribution as a `codex exec` worker inside its own scratch copy of captured inputs, so workers cannot touch the live tree and writes are disposable. `agy` has no equivalent capture-and-copy contract. Its headless mode runs agent turns in a real workspace (`cwd`), plus any directories granted with `--add-dir`. Since 1.0.0, workers run there with full access by default. The `full` custom-agent profile (a `tools:` list in `~/.gemini/config/agents/`) gives workers agy's own harness: file edits, `run_command` with `commandExecutionPolicy: eager`, `search_web`, `read_url_content`, agy subagents, workflows, and scheduling. It sets `inheritMcp: true` (a field the docs do not list) and has no `mcpServers`, `skills`, or `plugins` lists. On 1.5.12, tools from the user's installed agy plugins (MCP servers) and the user's custom agents were visible to full workers. Plugin MCP tools were also visible under an earlier profile with `mcpServers: []` and no `inheritMcp`, so the field's effect is unproven, and skills were not verified. Workers have no browser tools: agy 1.5.12 refuses `browser_*` and `browser_subagent` in a custom agent ("not found in registry"), even though its `init.tools` lists them, so browser-like work goes through the shell. Not every listed tool reaches the model either: on 1.5.12, `read_url_content`, `command_status`, `send_command_input`, `grep_search`, `list_dir`, and `find_by_name` stayed unexposed, and URL fetching worked with `curl` in the unsandboxed shell. Full roles get no `--add-dir`. In a live run with the run directory added, agy used it as the default command working directory, so commands ran outside the project. Full roles instead read the run directory by the absolute path their prompt lists, and the prompt tells them to run commands from the workspace root. Full roles have no writer limit, so several may edit the same worktree at once. agy starts each shell command in its own process group, so cancellation and timeouts kill the process groups of agy's descendants as well as agy's own; a tool that double-forks into an unrelated session before cleanup can still escape. Work a full worker starts with `schedule`, `run_workflow`, or `manage_task` that agy keeps outside the process tree may outlive the council; `cancel` and `reap` cannot reach it. A tool list only selects what the CLI offers the agent; it is not an OS sandbox. The capability-restricted profiles (`read`, `write`, `execute`) remain as opt-ins, unchanged: empty extension lists, no subagents, the run directory granted with `--add-dir`, and an explicit single-writer gate. Readers and editors in one council observe a moving worktree, which the skill tells Claude to account for.

**Wire protocol.** Codex emits JSONL records keyed by `type`. `agy --output-format stream-json` emits envelopes keyed by `event` (`init`, `step_update`, `result`), and with `--input-format stream-json` it reads one `{"event":"user",...}` message per stdin line. In live runs on 1.5.12, agy ran one turn per stdin message, emitted one `init` per process and one `result` per turn, and exited when stdin closed. Restricted roles get one user message, so they are exactly one turn. Unless the run was prepared with `--no-verify-turn`, full roles get a second user message on the same conversation, the forced self-verification turn described under [Claim verification](#claim-verification), sent only after turn one returns `SUCCESS` with a non-empty response, and never after the stream ended, failed its audit, or had no validated `init`. A later turn's `result` must follow a new `user_input` step, keep the stream's `conversation_id`, and advance `num_turns`; after a `result`, only the next turn's `user_input` may come first. agy 1.5.12 also renames some profile tools, both in the tool list the model sees and in step events. The runner maps each observed name back to its profile name: `read_file` to `view_file`, `write_file` to `write_to_file`, and `edit_file` to `replace_file_content`. That mapping also keeps a restricted writer from being killed on its first write. A `subagent_info` step from a full worker is recorded as a reply warning and marks the role non-replayable; from a restricted worker it is still fatal.

**Permissions.** `agy` headless mode has no prompt. Without a bypass, a tool that needs approval is *soft-denied*: the run continues and exits 0, and stderr names the tool. Reading outside `cwd` and `--add-dir` can end the turn with an empty response. Full roles, the default, therefore run with `--dangerously-skip-permissions`, an explicit `--mode accept-edits`, and session-only `--settings` that turn off the terminal sandbox, allow non-workspace access, and set `toolPermission` to `always-proceed`. The explicit mode matters because since agy 1.5.7 headless runs start in Auto mode, which turns the terminal sandbox on. Since agy 1.5.2 the bypass lets reads and writes outside the workspace through in headless runs. The user's deny rules, agy's system command denylist, and enterprise admin review still apply. The runner reports what they block (`result.denied_actions`) as a coverage warning. A full role whose `init.permission_mode` is not `always-proceed` fails, so it never runs half-restricted. The restricted opt-ins keep the old behavior: no bypass, the private run directory granted with `--add-dir`, and a prompt that names the directories they may read. Only restricted `read` roles retry once after an empty permission abort.

**Models.** Codex pairs a model with a separate reasoning effort. `agy models` advertises effort-specific variant IDs (a family name with a `-low`/`-medium`/`-high` style suffix), and `agy --effort` sets effort for a single run. The plugin pins the exact variant ID the user chooses. When the user names no model, the host omits `--model` so agy's configured default applies; it does not pick a model itself. Catalog IDs already encode effort, so when the user asks for an effort level, the host selects the catalog variant ID for it. A role that omits `model` may instead set the optional `effort` field (`low` through `max`, sent as `--effort`). agy 1.5.12 rejects `--effort` beside a catalog variant ID (`--model <id> conflicts with --effort=<level>`), so the runner refuses a role that sets both. agy's `init` does not report effort, so whether agy applied it is unobservable. There is no default effort. For pinned roles `init.model` is checked against the pin. Like codex-council, there is no built-in model list or preference; every choice comes from the user and the run's live catalog.

**Continuity.** Codex resumes with an explicit `continuity: resume`. `agy` resumes with `--conversation <id>`. Session identity here includes project, host session, task, role, exact model, effort when set, and capability profile, so a different model never inherits another model's thread.

**Plugin monitors.** Cursor Cult ships an experimental plugin monitor (`monitors/monitors.json`). This plugin instead has the skill run `follow` under the host's Monitor tool, because plugin monitors are experimental and run only in interactive sessions.

## Claim verification

Codex Council leaves claim checking entirely to the host. This plugin checks claims twice by default: once inside each full worker, then again by the host.

**Worker self-verification.** By default every full role gets a forced self-verification turn on its own agy conversation. `prepare --no-verify-turn` (`verify_turn: false` in `launch.json`) runs full roles single-turn instead (`verification_turn: "off"`). After turn one succeeds, the runner tells the worker to treat its draft as someone else's work. The worker re-checks every claim against live evidence (re-reading the lines, inspecting the diff, re-running tests) and uses its own subagents, briefed with only the claim and its evidence, to try to refute the most consequential claims. Before it accepts a refutation, it confirms that the cited defect actually exists. It fixes or retracts, repeats until the check finds nothing new, reports honestly, and writes a complete final report that replaces the draft. The reply's `response` is that final report, `draft_response` keeps the turn-one draft whenever a verification turn was used, and `verification_turn` (`completed`, `failed`, `not-run`, or `off`; null for restricted roles), `verification_turn_completed`, and `turns_completed` record what happened. The markdown report shows `verification turn: completed`, `failed`, `not-run`, or `off` for full roles. A completed verification turn means the worker re-checked its work, not that the answer is correct. If turn one fails, no verification turn is sent. If the verification turn fails, the role fails and `response` carries the unverified first-turn draft, with a warning that says so. If the process fails after a completed verification turn (nonzero exit, stall, or a late event), the role still fails, with a warning, but `response` keeps the verified final report. Restricted roles stay single-turn, and the report format stays free-form.

**Cost and evidence so far.** Live, the verification turn worked mechanically and once spawned its own skeptic subagent, but no live run has shown it changing an answer. It costs time and quota: a trivial task went from 88s to 211s, and three parallel high-effort workers plus their subagents hit the account's quota, so their verification turns failed. Size parallel councils to quota.

**Host reconciliation.** A full reply's verification turn may improve its evidence, but it never replaces the host's independent check. A `verification_turn` of `failed` means turn one was usable but the check did not complete, so the response is an unverified draft; `not-run` means turn one itself failed and no check was sent; `off` means the run was prepared with `--no-verify-turn`. Before reconciling, Claude sends consequential claims it can't settle quickly to independent read-only checks briefed only with the claim and its cited evidence, so they try to refute it rather than confirm the host's view. Before a refutation overturns a worker's claim, Claude confirms that the defect it cites actually exists (meta-verification). 0.2.0 shipped host checking as a separate dynamic-workflow command; 0.2.1 folded it into the single skill.

**Design inputs.** Two DeepSeek research sources inspired this design; nothing is copied from them. Honest self-analysis, refining until a check comes back clean, and checking a verifier's cited issues before accepting them come from DeepSeekMath-V2 ([arXiv 2511.22570](https://arxiv.org/abs/2511.22570)). Making verification forced rather than merely permitted comes from DeepSeek's [super-agent research prototype](https://github.com/deepseek-ai/dsh-superagent-prototype), whose notes report that an agent merely allowed to use a subagent tool did not call it.

## Documentation versus local CLI

The official docs and the installed `agy` 1.5.12 help now agree on most flags. Some flags are documented in only one place, and some defaults matter, so the runner passes explicit values and checks the installed help at preflight:

| Topic | Public docs (Nov 20, 2026) | `agy` 1.5.12 `--help` | Runner behavior |
|---|---|---|---|
| `--print-timeout` default | `0s`, meaning no limit (headless page and CLI reference) | `0s` (wait for the turn) | always passes a positive value, unchanged: `60m` or the operator's. agy 1.5.12 applies it per turn (a second turn finished after the limit had passed for the process as a whole), and the runner's own process watchdog allows turns × timeout + 5s |
| `--effort` levels | low through max, depending on the model (headless page, CLI reference, effort page) | low/medium/high/xhigh/max | sent only when a role that omits `model` sets the optional `effort`; preflight then requires `--effort`. 1.5.12 rejects `--effort` beside a catalog variant ID |
| `--mode` | CLI reference: `accept-edits`, `auto`, `plan`; not on the headless page; Auto is the default where available since 1.5.7 | accept-edits, auto, plan | `accept-edits` passed explicitly for full roles and restricted write/execute roles |
| `--settings` | not in the CLI reference flag table; the 1.5.8 changelog mentions files passed to it | session-only JSON of settings.json keys, never saved | passed for full roles; required at preflight; verified live on 1.5.12 |
| `--add-dir` | CLI reference flag table; not on the headless page | documented in help | passed for the private run directory, for restricted roles only. Full roles read that directory by absolute path, because on 1.5.12 an added directory became the default command working directory |
| Custom-agent `--agent` selection | headless page and CLI reference; profiles on the subagents page | `--agent` documented in help | passed; `init.agent` is checked against the profile |
