# Direct runner runbook

After `setup` and interactive `agy` authentication, use the Python runner from your target project. No inference happens in `doctor`, `prepare`, `discover`, or `check`. Run `setup` again after updating: it is idempotent and changes no settings or credentials. From 0.2.x it installs the new `agc-full-*` profile beside the three restricted ones. From 1.0.0 it installs the 1.0.1 restricted profiles `agc-read-cc5e5a5b5eef`, `agc-write-91558a374436`, and `agc-execute-70e52c3e3680`, whose hash names changed when they gained `inheritMcp: false`; the full profile `agc-full-7a01e9b77a7c` is unchanged. Until then, `check` refuses any role whose profile is missing and says to run `setup`. The 1.0.0 restricted profiles stay in place, unused, until you remove them.

```zsh
COUNCIL='/absolute/path/to/antigravity-council/plugins/antigravity-council/scripts/antigravity_council.py'
python3 "$COUNCIL" doctor --cwd "$PWD"
python3 "$COUNCIL" prepare --cwd "$PWD" --session-key 'manual-unique-session' --task-key 'specific-task'
```

Copy the returned absolute `run_dir`. Fill its `roles.json` and `context.md`, using the examples as structural templates, not as facts about your task. Do not leave placeholder model IDs; copy the exact IDs of the models the user named from discovery, or, when the user names none, omit `model` so agy's configured default applies. Do not pick a model yourself; the runner has no model preference. A role without `access` gets full access; `read`, `write`, and `execute` are restricted opt-ins. When the user asks for an effort level, select the catalog variant ID for it, because catalog IDs already encode effort. Set `effort` only on a role that omits `model`: agy 1.5.12 rejects `--effort` beside a catalog variant ID, and the runner refuses a role that sets both.

```zsh
RUN='/exact/run_dir-returned-by-prepare'
python3 "$COUNCIL" discover "$RUN"
# Write roles.json and context.md now, preserving the private directory.
python3 "$COUNCIL" check "$RUN"
python3 "$COUNCIL" start "$RUN"
python3 "$COUNCIL" follow "$RUN"
python3 "$COUNCIL" collect "$RUN"
```

For attached execution replace `start`/`follow` with `run`. Full roles need no flag and have no writer limit: several may edit the same worktree at once (live, four full roles fixing four different functions of one file at the same time all landed their fixes; edits to the same lines can still conflict). `--writer` applies only to a restricted role. A council may hold at most one restricted `write`/`execute` role, and it must be named when preparing: `prepare ... --writer exact-role-id`. Councils without a restricted writer, including full councils, share the per-worktree lock and run concurrently; a council with a restricted writer holds it exclusively, so other councils on that worktree wait for it. Reprepare a new run when changing launch authority. There is no safe assumption that an aborted full role or restricted writer can be replayed. The runner restarts a role automatically only when its saved conversation is dead and the error came before any tool work: it drops the saved conversation and starts that role fresh once, full roles included. Only restricted `read` roles also get the one transient retry and the headless permission-abort retry.

By default each full role runs two turns on one agy conversation: its answer, then a forced self-verification turn. `prepare --no-verify-turn` (`verify_turn: false` in `launch.json`) runs full roles single-turn instead. In the collected reply, `response` is the final report from the verification turn, `draft_response` is the first-turn draft, and `verification_turn` is `completed`, `failed`, `not-run`, or `off` (null for restricted roles), beside `verification_turn_completed` and `turns_completed`. The markdown report shows `verification turn: completed`, `failed`, `not-run`, or `off` for each full role. `completed` means the worker re-checked its work, not that the answer is correct. `failed` means the role failed; when turn one succeeded, `response` is its unverified draft. If the process fails after a completed verification turn (nonzero exit, stall, or a late event), the role still fails, with a warning, but `response` keeps the verified final report. The verification turn costs time and quota (live, a trivial task went from 88s to 211s, and three parallel high-effort workers plus their subagents hit the account's quota, so their verification turns failed); size parallel councils to quota. `--print-timeout` (set at `prepare`, default `60m`) is passed to agy unchanged, and agy applies it per turn; the runner's own process watchdog allows turns × timeout + 5s. Full workers may use agy's own subagents; the reply then carries a warning saying so. Restricted roles stay single-turn and may not use subagents.

## Recovery

`status "$RUN"` returning `running` or `finishing` is not completion. Reattach `follow`, optionally with `--after-sequence N`. `follow --timeout 30` stops only the follower after 30 seconds and leaves the council running; it is not a cancel command.

Use `cancel "$RUN"` for deliberate cancellation. If it cannot stop a verified live supervisor, review its diagnostics before `cancel "$RUN" --force`. After a SIGKILLed supervisor, `status` can show `aborted`; `reap "$RUN"` attempts to terminate verified recorded worker groups. Do not reap an active or uncertain run. Collect partial evidence with `collect "$RUN" --partial`. agy starts each shell command in its own process group, so cancellation and timeouts also kill the process groups of agy's descendants; before 1.0.0 a cancelled worker's command survived as an orphan, and live testing found none surviving after this change. A tool that double-forks into an unrelated session before cleanup can still escape. Work a full worker started with `schedule`, `run_workflow`, or `manage_task` that agy keeps outside the process tree may outlive the council; `cancel` and `reap` cannot reach it, so stop it yourself if it should not continue. In live runs, `schedule` was used only as an in-turn wake-up timer and was cancelled early.

When the model catalog changes, rerun discovery before authoring a new directory. When quota or a model pin fails during execution, preserve its identity and report the gap. Never replace one model family with another, or an explicit higher variant with a lower one, without user direction.

Headless command denial is not necessarily a failed whole run. Under full access, a denied command or file action means one of the user's own deny rules, agy's system command denylist, or an enterprise admin policy blocked it. Inspect `denied_actions` and the warnings in the role's reply, and the raw stderr. A full role whose reply shows a `permission_mode` other than `always-proceed` failed as a protocol error, for example because admin policy keeps review on. A restricted role's denial is a soft denial: configure a scoped operator allow rule, or reprepare with a full role if the user wants that. Since 1.0.1 a restricted `execute` role runs its commands in agy's terminal sandbox without a prompt (`toolPermission` `proceed-in-sandbox`), and that sandbox has no network: live, `curl` to an external site got HTTP 403 from the sandbox proxy. A network failure there is not a tool denial. Through 1.0.0, every command such a role tried was denied. Never claim the tests ran merely because the agent answered.

## Retention and uninstall

Runs, raw streams, and continuity files remain under the council state directory. After confirming all related supervisors and workers have ended, remove obsolete runs according to your data-retention policy. Keep any evidence you need before deletion. Deleting a session record loses continuity but does not remove the CLI's own stored conversation.

Remove the Claude plugin with `claude plugin uninstall antigravity-council@antigravity-council` using your installed CLI. Profile setup prints the exact files it created; remove only those files when no council is using them. Never delete the entire `~/.gemini/config/agents` directory, which can contain unrelated agents. Global Antigravity settings and credentials were not modified; the `--settings` passed to full roles and restricted execute roles is session-only and never written to `settings.json`.
