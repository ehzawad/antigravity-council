# Security model

This plugin coordinates trusted, authenticated local agent CLIs. By default its workers have full access to the machine as the user. It is not a secure multi-tenant service, an untrusted-code container, an OS sandbox, or a proof that model-generated actions satisfy a user's intent.

## Default: full access

A role that omits `access` (or sets `full`) launches with `--dangerously-skip-permissions`, `--mode accept-edits`, and session-only `--settings` that turn off agy's terminal sandbox, allow access outside the workspace, and set tool permission to `always-proceed`. The worker runs as the user's OS account. It can read and write any file that account can, run any command without approval and without a terminal sandbox, use the user's network, search the web, and fetch URLs (on agy 1.5.12, with curl in the shell). It can also use agy's own harness: start subagents, run workflows, and schedule work. In live runs, a full worker successfully called a tool from the user's installed agy plugins (an MCP server), the user's custom agents were visible to full workers, and workers listed the user's plugin skills (model self-report). Several full workers may edit the same worktree at once. This is the configured default, not a per-run authorization. The host still asks the user before commits, pushes, deploys, publishing, or expanding scope, and the worker contract tells workers the same, but that is an instruction to a model, not an enforced control.

Some vendor controls still apply: the user's own deny and ask rules (documented to take precedence over allow), agy's system command denylist, and enterprise admin policy. Actions they block are returned in agy's `result.denied_actions`, kept in the reply, and reported as coverage warnings. If a policy keeps review on and `init.permission_mode` is not `always-proceed`, the role fails rather than running half-restricted. The full profile's tool list chooses which built-in tools the CLI offers the worker. The profile sets `inheritMcp: true` (an undocumented field) and has no `mcpServers`, `skills`, or `plugins` lists. Inheriting MCP is agy's default: live, a profile with no `inheritMcp` key and no lists also called a plugin MCP tool, and only `inheritMcp: false` switched MCP off. Assume whatever the user has configured in agy can reach full workers. Browser tools do not: agy 1.5.12 refuses them in a custom agent ("not found in registry"), so browser-like work goes through the shell. None of this is a security boundary, since `run_command` alone reaches everything the account can.

## Implemented controls

Inputs and state are private, user-owned files. Strict schemas, immutable intent hashes, input hashes, exact model pins, content-addressed worker profiles with startup hash checks, workspace locks, and process-identity checks prevent specific accidents and fail closed on missing evidence. Profile setup refuses conflicting content. The runtime does not change global settings (`--settings` is never written to `settings.json`) or deliberately export credentials.

Restricted roles are explicit opt-ins. `read` workers get only the documented file-reading/search tools, with paths fenced to the workspace and run directory. `write` adds file tools; `execute` additionally gets shell under agy's `--sandbox`, with session-only `--settings '{"toolPermission":"proceed-in-sandbox"}'` so its commands run in agy's terminal sandbox without prompting. Before 1.0.1, headless agy denied every command of a restricted executor (`request-review`), so the role could edit but not run commands. Live on 1.0.1, a command ran and an outbound request got HTTP 403 from the sandbox network proxy. At most one restricted write/execute role is allowed, it must be named with `--writer`, and its council takes an exclusive workspace lock. Its prompt says it is the only restricted writer and that full-access workers, if any, may also edit. Restricted profiles set `inheritMcp: false`, keep empty `mcpServers`, `skills`, and `plugins` lists, and have no subagent tools. `inheritMcp: false` is what keeps MCP out: the 1.0.0 restricted read profile, with `mcpServers: []` but no `inheritMcp: false`, successfully called a plugin MCP tool. The lists do not keep skills out: workers listed the user's plugin skills even with `skills: []` and `plugins: []` (model self-report). Restricted init/tool events are checked, and a tool step outside the profile or any nested subagent activity fails the role; an MCP call fails the audit only after the call ran. agy 1.5.x reports some steps under new names; only the observed aliases `read_file`, `write_file`, and `edit_file` are mapped back to their profile tools. A reviewer has no shell just because a command sounds read-only: redirections, test fixtures, language startup hooks, and build scripts can mutate files.

Restricted roles keep permission bypass off. `--unrestricted-shell` remains only as a legacy option that adds it to a restricted execute role in place of the `proceed-in-sandbox` setting. `--sandbox` is vendor behavior, not containment this Python process independently provides. File-edit permission does not authorize commits, deployment, publishing, or remote operations.

## Limits that remain

Processes run as the same OS user. A full worker can read and change anything that account can reach: other repositories, plugin code and stored runs, shell history, SSH keys, and cloud, Git, or package-registry credentials under `~`. A restricted executor can also reach files a reader cannot. A hash and 0700 directory do not protect against that same user's process. Only an OS-level boundary can offer stronger containment.

Whatever a worker reads is sent to the selected provider, including credentials or other files outside the workspace if a worker reads them. The plugin does not redact code or apply a data-loss-prevention policy. Raw streams, prompts, and error messages may include secrets. Stored files use restrictive modes, but operators remain responsible for retention, backups, and who can access their account.

Repository files, logs, issue text, web pages, and fetched URLs are untrusted input. The worker contract tells workers to treat them as evidence, not instructions, but that is guidance to a model. With full access, injected text can drive shell commands, network requests, file edits, subagents, scheduled work, and any MCP tools that reach the worker, including sending local data elsewhere.

Custom-agent configuration is a vendor contract. CLI changes, global hooks/MCPs/plugins, profile shadowing, and startup behavior can change what workers do. Known workspace profile shadow paths are refused; `init.agent`, a pinned `init.model`, and for full roles `init.permission_mode` are checked; restricted roles' tool events are audited. A full role's tool step outside its profile list, and its use of agy subagents, are only recorded as warnings. This is not exhaustive hostile-configuration analysis, and an observed tool event can arrive after work has begun. The original workspace and machine configuration must be trusted. The full profile does not exclude the user's agy MCP servers, plugins, or skills: a full worker successfully called a plugin MCP tool, and custom agents were observed reaching full workers. Observed on `agy` 1.4.4: a read-only worker reported a system message asking it to configure a user-installed agy plugin (one that ships hooks), despite the profile's `plugins: []`. The worker declined, but enabled agy plugins, their skills, and hooks can still reach restricted workers too; on 1.5.12, workers listed the user's plugin skills under every profile tried.

Retries are deliberately narrow. A dead saved conversation is dropped for every role, and any role, full included, restarts fresh once when the error came before any tool work. Otherwise only restricted read roles are retried (one transient retry and one headless permission-abort retry), and full roles and restricted mutators never are, because they may have edited files or run commands. Even read-only retry safety depends on CLI reports. No exactly-once execution is promised. Successful transport output is not proof of correctness, clean tests, or successful command execution; headless permission denials can be soft failures. A full reply's `verification_turn: "completed"` means the worker re-checked its work in its own forced verification turn, not that its answer is correct; the turn may improve the evidence but never replaces the host's independent check, and before a refutation overturns a worker claim the host confirms the cited defect exists.

Process groups enable best-effort cancellation. agy starts each shell command in its own process group; before 1.0.0 a cancelled worker's command survived as an orphan (observed live). The runner now walks agy's descendants at kill time and kills their process groups too, and a live cancel after the fix left no surviving command. A tool that double-forks into an unrelated session before cleanup can still escape, and other detached daemons, background jobs, and tools that reparent or run externally may outlive a killed worker. Work a full worker starts through agy's `schedule`, `run_workflow`, or `manage_task` that agy keeps outside the process tree may outlive the council, and cancel and reap cannot reach it (in live runs, `schedule` was used only as an in-turn wake-up timer and was cancelled early). A report of supervisor exit is not a universal proof that every descendant in the system stopped. `reap` only signals verified recorded worker identities after a verified supervisor death. Reboots, PID namespaces, filesystem issues, and suspended hosts remain external failure modes.

Several full workers, and their agy subagents, may edit the same files concurrently. The plugin does not lock or merge individual files; workers are told to re-read before editing, but interleaved or lost edits are possible. Full-only councils share the workspace lock, so they are not serialized against each other. Only a restricted writer excludes other fleets. Manual editors and other tools do not participate in this plugin's lock. Readers can inspect intermediate edits. Independent verification must be repeated on settled artifacts.

## Recommended operation

Use full access only for trusted repositories on a machine where you accept that workers act as you. For untrusted repositories, unfamiliar dependencies, or tasks that read untrusted web content, use restricted roles (start with `read`) or an isolated VM/container or a restricted OS account. Add deny rules for commands you never want run. Full access needs agy 1.5.12 or later. Run the opt-in billable live smoke test on the installed CLI version before depending on full-access behavior. Keep authenticated local agent access away from public web services. Never claim the offline fake-CLI suite certifies the current vendor binary.

Report problems privately to the repository owner before publishing sensitive logs. The package has no telemetry endpoint and does not send reports anywhere beyond the CLI requests the operator launches and whatever network requests its workers make.
